# 代码改动规范

按顺序执行，不要跳步。

## 1. 先理解，再动手
- 用 `code_map` 看目标文件的结构，不要上来就整文件读。
- 用 `grep` 找关键符号的所有引用点，确认改动的波及范围。
- 如果是陌生项目，先 `repo_overview` 看整体，再 `run_tests` 跑一遍基线（知道改动前是什么状态）。
- 明确说出你要改什么、为什么改、影响哪些文件。

## 2. 最小改动原则
- **优先 `edit_file` 精确替换**，不要用 `write_file` 重写整个文件（容易丢内容）。
- 保持现有代码风格（缩进、命名、注释语言、import 顺序）。
- 不要顺手"优化"与任务无关的代码——这是引入 bug 的主要来源。
- 不要删掉看不懂的代码；先 `grep` 确认它是否还有用。

## 3. 改完必须验证
- 至少跑一次相关测试：`run_tests(path=..., target=改动的测试文件)`。
- 没有测试就自己写一个最小复现：用 `python_exec` 或 `shell` 直接跑。
- 改前端/配置类文件，至少做一次语法/加载检查。
- **验证结果要如实报告**：跑不过就说跑不过，把真实报错贴出来，不要美化。

## 4. 收尾
- 用 `git(action='diff')` 看一遍自己的改动，确认没有多余文件、没有调试残留（print、临时 TODO）。
- 临时脚本、探测文件、中间产物要删掉（或放到工作区之外的临时目录）。
- 简洁说明：改了什么、为什么、验证方式、还有什么已知未解决。

## 禁区
- 不要为了让测试通过而改测试断言（除非测试本身写错了，并要明确说明）。
- 不要在代码里硬编码密钥、绝对路径、个人环境信息。
- 不要提交 `.env`、数据库、大二进制文件。
