# 代码评审

先看 diff 全貌（`git(action="diff")`），再逐项过。**按严重程度排序输出，不要平铺。**

## 1. 正确性（最高优先）
- [ ] 逻辑是否真的实现了需求？边界条件（空、0、负数、超长、null/None）处理了吗？
- [ ] 循环/递归的终止条件对吗？会不会死循环？
- [ ] 异步/并发：有竞态吗？共享状态加锁了吗？异常路径会泄漏资源吗？
- [ ] 错误处理：异常被吞了吗？失败时状态一致吗（部分写入）？
- [ ] 类型/单位是否一致（字符串 vs 数字、秒 vs 毫秒、字节 vs 字符）？

## 2. 安全
- [ ] 用户输入是否被直接拼接进 SQL / Shell / 路径 / HTML？（注入）
- [ ] 路径拼接有没有防目录穿越（`../`）？
- [ ] 有没有硬编码密钥、token、内网地址？
- [ ] 反序列化不可信数据（pickle / eval / yaml.load）？
- [ ] 权限校验是否可绕过？越权访问他人数据？
- [ ] 日志里会不会打印敏感信息？

## 3. 性能
- [ ] 有没有 N+1 查询、循环里发请求/读文件？
- [ ] 大数据量会不会全量加载进内存？
- [ ] 有没有重复计算、可以提前退出的循环？

## 4. 可维护性
- [ ] 命名是否表达意图？（`data` / `tmp` / `x` 是坏味道）
- [ ] 函数是不是太长？（>60 行通常该拆）
- [ ] 魔法数字有没有命名常量？
- [ ] 有没有复制粘贴的重复代码？
- [ ] 注释是否说明"为什么"而不是"做了什么"（后者读代码就知道）？
- [ ] 与现有代码风格一致吗？

## 5. 测试
- [ ] 新增逻辑有测试吗？
- [ ] 测试断言是否真的能捕获错误（而不是永远为真）？
- [ ] 改了行为但没改测试？

## 输出格式
```
## 必须修（会导致 bug / 安全问题）
1. [文件:行] 问题描述 → 建议改法

## 建议改（质量 / 可维护性）
...

## 做得好
...（具体点出，不要客套）

## 验证情况
（跑了什么测试、结果如何）
```

只报真问题，不要为凑数而列风格偏好。不确定的地方明确说"需要确认"。
